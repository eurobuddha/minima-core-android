PANDAMONIUM — BATTERY AND EFFICIENCY PLAN
2026-10-11 | Source baseline: dd4dda3, version 1.9.13, versionCode 84

RECOMMENDATION

Sleep invisible presentation work, not the node or financial obligations.
Start with the core tabs and retained screens; measure before changing any
background settlement, keep-alive, wake-lock or alarm behaviour.

This is a source-based plan, not a measured battery result or a guarantee of
perfect operation. No application code was changed, built, installed or tested
for this review. Existing test source was inspected, not rerun. No device was
accessed. No application-code working-tree diff was present; the observations
below concern existing behaviour, not newly introduced patch defects.

The existing graph was queried first, but returned outdated package paths and
limited lifecycle information. The conclusions below use current source.

1. WHAT THE CURRENT CODE DOES

Paths are relative to /Users/eurobuddha/Projects/minima/apks/base unless stated.

* Core tabs have no deselection lifecycle: main/MainActivity.java:140 leaves
  onTabUnselected empty. MainAdapter constructs all five screens and
  refreshAllViews runs when the service connects.
  Source directory: app/src/main/java/com/eurobuddha/minimacore/.

* main/MainActivity.java:494-500 refreshes the Node dashboard and footer on
  every block, even when another tab or another retained activity is visible.
  HomeView.readDashboard reads keys, peers and network; the footer separately
  reads keys. Coalescing bounds bursts but does not eliminate hidden work.

* main/views/logs/LogsView.java:134-137 attaches a live log sink during refresh;
  it is detached only on activity destruction at line 241. Since all views are
  refreshed on connection, hidden Logs can receive text append/scroll work
  without the user first selecting it. LogBuffer already retains a bounded
  600-line tail independently of the visible sink.

* app/src/pandamonium/java/com/eurobuddha/minimacore/integrated/HistoryTabView.java
  starts HistoryScreen subscriptions with the whole activity, not the selected
  tab. HistoryScreen sync completion can reload up to 3,000 display rows and
  refresh ownership while its tab is hidden. IMPORTANT: history capture is an
  archive, not merely a display refresh; the node eventually prunes records.

* main/views/balance/BalanceView.java has a 10-second freshness-label timer.
  It checks visibility for metadata work, but window attachment is not the
  same as being the selected tab in a foreground activity.

* integrated/mail/src/main/java/com/eurobuddha/mail/MainActivity.java:214-227
  runs a 30-second freshness-label timer until destruction. onStop removes
  event subscriptions but not this timer. This is UI work, not a network poll.

* Several embedded apps already unsubscribe onStop. PandaDEX already stops
  activity polling onPause; PandaPools stops its block poll onStop and its
  Activity tab has a visibility-gated poll. Preserve these existing controls.

* Integrated node calls already use an in-process transport. Do not invent
  per-tab connection teardown: there is not a separate node socket to close
  for each of these screens.

* service/MinimaService.java:139-148 holds CPU and Wi-Fi locks for node uptime.
  Sleeping UI will not make this full-node app behave like a dormant wallet.
  The actual battery contribution of each subsystem remains unmeasured.

3. IMPLEMENTATION ORDER

PHASE A — Establish the baseline

Measure the existing version on an agreed test device with a disposable wallet:
Wallet parked; each core tab parked; all sidebar apps visited then backgrounded;
screen off; and representative active financial work. Separate initial chain
sync/history backfill from steady-state measurements.

Collect commands by owner/type, timer executions, UI renders, CPU time, network
traffic, wake-lock duration and energy estimates using Android profiling tools.
Do not log seeds, keys, signing payloads or private message content. Repeat
before/after runs under matched network, brightness and node conditions.

PHASE B — Core UI sleep (first implementation release)

Connect MainActivity + MainAdapter + BaseView to an idempotent visibility state:
selected tab AND visible host. Retain screen state; do not destroy/recreate a
tab merely to put it to sleep. Preserve multi-window visibility semantics.

On hide: stop presentation timers, detach UI-only subscriptions, invalidate
obsolete rendering and mark data dirty. Do not close shared transport or cancel
an in-flight mutation. Prevent a late read callback from restarting a timer.

On show: display the retained snapshot, visibly mark stale data, and request
one coalesced reconciliation; restart only the necessary visible UI timer.
Keep fresh checks at send/sign/confirmation boundaries regardless of UI cache.

Apply first to:
  - Logs: detach only the display sink; retain LogBuffer, operational observers
    and Terminal IDE persistence. Render the retained tail once on return.
  - Node dashboard: defer its display reads while hidden.
  - Footer: refresh only while the core host is visible; avoid duplicate keys
    reads through a narrowly scoped shared result, not a broad allowlist change.
  - Wallet: stop hidden freshness/metadata timers and reconcile on return.
  - Apps: defer display refresh while hidden, but retain pairing/permission
    state updates and security checks independently of the screen.

PHASE C — History and remaining screens

Separate History's archive capture from its list rendering. Keep current capture
behaviour initially; suppress hidden list queries, rendering and display-only
ownership refresh where safe. Reuse HistoryDb/HistorySync, preserving deduplication
and backfill state. Do NOT just call HistoryScreen.close() or HistorySync.cancel()
on tab deselection: close is destructive and cancel currently permanently marks
that sync instance cancelled. Any reduced archival cadence needs explicit
retention/catch-up tests before adoption.

Tie Mail's freshness timer to visibility and recompute its label immediately on
return; leave mail send/scan completion and message persistence intact.

Audit remaining sub-tabs for rendering, animation, price-preview and metadata
work after deselection. Reuse each app's existing lifecycle stops. Do not treat
an entire feature as disposable simply because its presentation is hidden.
Defer lazy construction of entire screens: some register activity-result
launchers during construction, which must respect Android registration timing.

PHASE D — Reduce redundant reads, without slowing essential work

Where supported, use existing direct block/balance events for presentation
refresh instead of another periodic node read. Use single-flight coalescing,
refresh on resume/reconnect, and retain a low-frequency reconciliation fallback:
the event bus is not durable and events may be missed or coalesced.

Keep order discovery and cross-chain checks separate from local block-driven
display refresh. Do not assume a Minima block event substitutes for an Ethereum
or market deadline. Avoid polling faster simply because local calls are cheap.

PHASE E — Background services (separate, higher-risk work)

Inventory persisted obligations before changing any cadence. Preserve swaps,
maker orders, pool maintenance/collection, Casino reveal/resolve, FutureCash
guardians, pending confirmations and uncertainty/recovery records.

PandaPools already gates work to owned pools. Reuse that obligation-based pattern
where compatible; first prove that no outstanding recovery or externally
discoverable offer remains. Preserve foreground/background single-writer handoff.

Only after profiling, consider batching compatible maintenance wakeups and
releasing per-pass timed locks on actual completion, with timeout fallback.
Keep existing deadline and Doze/reboot recovery guarantees. Do not replace the
existing exact-alarm/worker stack with a UI Handler loop, or wholesale merge
services in the first release. The core CPU lock is already held, so reducing
feature lock time alone may not yield additional device sleep.

Core node lock/network-policy changes are a separate experiment, not part of
safe tab sleep. Never quietly trade away node availability for a battery claim.

4. RELEASE GATES — “STILL WORKS” MUST BE DEMONSTRATED

* Hidden UI: after currently running work settles, zero recurring UI-only
  timers/renders from sleeping screens. Archival and financial work are counted
  separately, not incorrectly classified as a failure to sleep.
* Resume: one logical reconciliation per dirty screen, no duplicate subscriptions
  or timer chains, no stale callback restarting hidden work.
* Navigation: rapid tab/sidebar switches, Back, rotation, background/foreground,
  screen lock, multi-window and process recreation preserve forms and state.
* Transactions: leaving any screen during build/sign/post/confirmation neither
  cancels required work nor repeats a write; uncertainty markers survive.
* Background: test active swaps, published makers, owned pools/withdrawal recovery,
  Casino obligations and FutureCash guardians with screen off, network loss,
  Doze, reboot and node restart. Test foreground/service handoff for one writer.
* Data: History backfill/catch-up and retention remain complete; Logs retain the
  existing bounded tail; mail and file operations finish without lost results.
* Run existing refresh/event/read-policy, financial safety and navigation tests;
  add the missing per-tab lifecycle and late-callback tests. Check all core
  flavors so shared BaseView/MainAdapter changes do not regress other builds.
* Repeat baseline measurements and report actual results, including cases where
  savings are small. No percentage saving is defensible from source alone.

Update reproducible integration adaptations when changing imported code,
especially scripts/adapt-pandamonium-navigation.py and the relevant direct
adapter/import pipeline. Verify regeneration does not erase the change.

Ship small reversible changes with the repository-required versionCode and
versionName bump, a versioned installer filename and unchanged wallet storage.
Do not install on a funded phone as part of unattended validation.

FIRST DELIVERY: core visibility lifecycle + sleeping Logs/Node/Wallet UI + Mail
freshness timer control, with regression tests and before/after measurements.
History display separation follows without first disabling archival capture.
Leave financial scheduling and core node availability unchanged initially.
