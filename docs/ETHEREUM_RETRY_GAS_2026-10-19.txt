Ethereum unknown-payment retry and standalone ETH Wallet parity — 2026-10-19

Findings and reproduction
MAJOR: an unknown manual payment was identified by recipient, calldata, value AND
gas limit. A fresh estimate changed that identity. The retry path could replay the
old transaction, allocate another nonce and submit the same payment again. A receipt
for the original did not prevent this second payment when the estimate changed.
MAJOR: replaying saved bytes could exceed a lower gas price just reviewed by the
caller. Existing fee-cap checks bounded the new request, but not the older signature.
Four regressions using EthereumTransactionsTest's public key, in-memory store and
fake RPC all failed before the fix and passed afterward. No real transaction used.

Repair and reuse
Kept the existing journal, decoder, intent builder, exact-hash reconciliation and
account lock. Unknown manual retries now compare payment fields using the stored
gas limit. The original receipt is checked first. Unsettled retries retain that gas
limit and cannot exceed either newly reviewed fee field. If the new gas limit or
price is below the saved attempt, return its existing uncertain hash without signing
or broadcasting. Eligible fee replacements still use the original nonce/payment.
Stable automatic operation identities keep their existing strict intent checks.
No store migration, private-key copy, new dependency or transport change.

Standalone port
apks/ethwallet now uses byte-identical EthTx.java, EthRpc.java and the shared
EthereumTransactions.java. Its existing minimaapi.aar has no ethereum classes;
the reviewed journal is included as source in the same namespace. Existing R8 rules
already preserve that namespace and web3j crypto/RLP. Activity startup initializes
the journal; unknown submissions save the exact hash for Last transaction and show
an uncertainty message instead of 'Send failed'. IPC derivation, secure key storage,
manifest backup rules, account/endpoint review guards and asset identity stay intact.
