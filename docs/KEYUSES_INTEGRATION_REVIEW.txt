KeyUses integration — Pandamonium 1.9.96 / code 167

Code Review
Summary
The native KeyUses screen audits the embedded node and both deterministic key
families, with an optional minimaWallet public-key set. No seed-entry UI is included.
It uses the existing Future Cash audit engine/client and wallet readiness/storage
bridges. Signing, transfers, counter writes and seed changes are outside this flow.

Reuse and provenance
Native UI: apks/keyreuses 0.1.4, 263ac87e173dd82ab8e0b00e40d70b3c252665fc.
Dual-family recipe: mds/keyuses phrase/derive.js and scanner/DeriveVectors.java,
be26bf7c6f13c6f0ef68cc54ec419b51ab9fead6 (phrase build 0.1.8).
NodeAuditKeys reuses WalletCore.derivePrivateSeed and the node TreeKey implementation:
64 indices with shape 64/3, and 32 indices with shape 128/4. The same seed/index
modifier hashing is used for both families. No JavaScript crypto port was added.
All 16 known public fixture vectors are preserved in keyuses-derive-vectors.json:
SHA256 c5352367d308445fc0780249c9d50b3dae7119d8f707e5ed5ee4d9d1272ce64c.
These fixture seeds are test data from the donor, not account credentials.

Shared building blocks are integrated/futurecash-next KeyAudit, AuditApi and
MinimaAddress, and integrated/wallet EmbeddedWallet, WalletCore and PublicAuditKeys.
The native donor's unchanged helper/test snapshots are retained for reproducibility;
the screen explicitly imports the shared Future Cash audit implementation.

Review boundaries
Read canonical bridge, selection, lifecycle and copy changes with callers, node SQL,
wallet public-descriptor validation, shared engine/client, source adapter, tests,
manifest, navigation, catalog and version wiring. Canonical importer regeneration
preserves every prior integrated module except the new wallet bridge/test additions.
An initial Robolectric harness failure was fixed by assigning the real activity
theme to the test subclass before creation. The SHA3 self-test failure message now
survives language changes and audit execution checks the same guard directly.

The generic imported navigation tag originally targeted the whole vertical audit
container. Review corrected this using AtomiX's existing self-owned menu pattern:
a top-row button is rebuilt with localized accessibility text and retains access
to the shared drawer when the language changes.

No remaining correctness or security finding in the integration review.
Verdict: Approve, subject to the recorded build/device validation below.

Limitations
A newly derived alternate-family key has no reliable stored counter; it remains
unknown even when remote evidence arrives. A reuse finding still takes precedence.
The public audit relies on archive coverage and default signed-by addresses; a clean
response is not proof of future signing safety. No account seeds or signing counters
were changed for device testing.


1.9.97 / code168 — display revision after Fold feedback

The 1.9.96 live audit successfully returned classic spend history and the node's
block-family counters. The owner identified three display issues: continuous
numbering, off-screen status colours, and unknown labels despite available public
history. Re-read mds/keyuses/phrase/index.html renderResults/renderRows (0.1.8) and
the native donor row/status/card helpers before adapting the presentation.

Changes
- Separate highlighted Classic, Blocks-as-keyuses, and distinct minimaWallet
  sections, numbering restarted within each section. Shared keys keep their source
  labels and occur once. The audit identity/index is retained for data mapping.
- Weighted columns fit the viewport without HorizontalScrollView. The original
  status chip/colours move into the address cell. Numeric text sizes down within
  a bounded range to keep counters visible on narrow phones.
- Phrase-style USED n / UNUSED from public archive history, and original red/amber
  REUSED counts. Unknown means missing/inconsistent public evidence. No stored
  counter is invented for derived classic keys.
- Shared KeyAudit adds publicChecked/publicComplete, factoring the existing shape
  and endpoint/address checks. Existing valid/checked/complete semantics and all
  Future Cash financial gates are unchanged. KeyUses uses public completeness for
  its history display and retains local-counter heuristic warnings where available.
- English, Chinese, Russian and Ukrainian text updated together.
