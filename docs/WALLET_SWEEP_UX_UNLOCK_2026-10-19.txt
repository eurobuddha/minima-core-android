Unlock diagnosis and fix
SeedVault.open creates a fresh NodeKeyUses with its own WalletCore. Audit export and
counter reconciliation ask for all64 public keys; that core did not use the persisted
AddressBook cache. This rederived classic TreeKeys every unlock. Standalone has no
NodeKeyUses provider, so this particular repetition is integrated-only.
Read AddressBook.java, WalletCore.java, NodeKeyUses.java, PublicAuditKeys.java,
SeedVault.java/VaultBlob.java and VaultCrypto.java plus sibling wallet/NFTwallet/utxo
candidates and counter/audit/startup tests. Existing AddressBook/audit public metadata
is not authenticated: trusting it for node counter lookup could hide a higher counter
by substituting the public key. It is unsuitable as signing-counter authority.
New CachedPublicKeys supplies NodeKeyUses' existing IntFunction hook. It uses the
unchanged WalletCore.getPublicKey derivation on a miss and existing VaultCrypto HKDF
plus authenticated container for persistence. Only public keys are cached, bound to
the decrypted seed with a domain-separated derived secret. No private keys, seed,
passphrase, counters or trust flags are stored in this cache. The optional cache uses
one KDF iteration with a seed-derived256-bit credential; human-passphrase vault KDF
stays210000. Header work and payload size are bounded before decryption. Invalid,
missing, corrupt, wrong-seed or failed-write caches fall back to derivation. It cannot
reset counters or permit signing. Current node/local counter reconciliation, reservation,
locking, persistence and vault authentication remain unchanged. Existing installations
populate this protected cache on their first successful unlock; subsequent opens reuse
it. No measured Fold unlock duration is claimed. No standalone unlock change needed.
