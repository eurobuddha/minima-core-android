Finding and repair
MAJOR: executeDeal reset its status to AGREED on any engine error, including an
error after its first lock was submitted. Retrying generated a new secret/hash,
so the Ethereum journal's per-hash idempotency did not prevent a second lock.
The Minima path had the same reset. With the original controller, both corrected
real-engine regressions failed: expected EXECUTING, actual AGREED.
The initial test fixture incorrectly changed an immutable deal side; it was fixed
before the before/after result was accepted. Tests use real SQLite, public synthetic
identities, mocked node/network calls and a deterministic worker, with no transactions.

StartCb.onPrepared now saves the exact recovery hash into the executing deal before
submission. False or failed persistence stops dispatch. Prepared failures retain the
hash and cannot reopen agreement. Pre-preparation errors can still retry. Callbacks
are synchronized and checked against the exact persisted snapshot; late, duplicate,
invalid-hash or mismatched success cannot mutate another attempt or notify a peer.
Restart reuses the existing expireStale/resendExecute and chain-driven swap recovery.
The Minima wrapper forwards onPrepared. Ethereum failure callbacks keep the existing
UI-thread delivery contract. Messages cover English, Chinese, Russian and Ukrainian.

MAJOR: initiator recovery saved secret, requested amount and swap in separate writes,
and ignored failed secret/request inserts. prepareInitiator now saves them in one
SQLite transaction, checks secret/request persistence, and uses the existing checked
swap insert. A failure rolls the entire set back and prevents dispatch. Existing
secrets cannot be replaced with a different preimage.

Code review
Read the changed canonical adapter/snippets, generated Java, callback callers,
real SQLite tests and localization entries. Both chain directions save the swap
before invoking the synchronous persistence hook and before sending their first leg.
No signing algorithm, destination, seed, key counter or negotiated amount was changed.
The success callback requires the saved hash; unknown outcomes retain recovery state.
The notification avoids claiming a first-leg failure when its outcome is unknown.
The preparation error refers to the swap lock specifically: an earlier ERC20 approval
may already have been sent by the unchanged allowance flow.
