Sweep worker correction — Pandamonium2.0.17/code212 —2026-10-19

User report and evidence
After taking manual control and executing Sweep on2.0.16, the user reported failure
and misleading attribution to the node. Read-only Fold screenshot hierarchy saved at
build/localization/fold-sweep-2.0.16/sweep-user-failure.xml showed:
  Node accepted0 of1 transactions.
  Minima: Could not prepare this transaction. No broadcast was attempted for this batch.
No agent retry, signing, posting, seed/counter modification or pending-data deletion.
A later UI read stopped at the app boundary when the user switched apps.

Cause
SweepFlow.current() wraps MainActivity.sessionAuthorization(), whose idle-UI policy
requires !mSession.work().busy(). Sweep called current() from INSIDE runSigningWork's
worker lambda. WalletWork deliberately holds busy=true during that operation, so
Sweep threw before TxnFactory.buildSend/buildWholeTransfer. The error callback then
replaced the actual exception with a generic preparation message. This fault belongs
to the integrated adaptation; it is absent from standalone wallet's synchronous flow.
It is not an invalid external destination and not a node transaction-building error.

Reuse and minimal repair
Read standalone wallet/app/src/main/java/com/eurobuddha/wallet/SweepFlow.java next/run
and comms/NodeLink.java publish. Read the integrated MainActivity authenticated/signing
worker, sessionAuthorization, resolveInputs and normal confirmSignAndPublish flow;
WalletWork, SweepPlanner and existing Sweep/worker/message tests were inspected.
Removed only the redundant idle-UI check inside the worker. Reused runSigningWork's
existing captured-connection, vault-generation and signing gates, matching normal Send.
Pre-scheduling and callback current() checks remain; counter snapshot, reservation,
size recovery, pending transaction persistence and exact-byte replay are unchanged.
Reused WalletMessages.error/message for meaningful local failure reasons. Input-coin
resolution is now distinguished from local preparation/signing. The result heading
states broadcast acceptance rather than suggesting the node builds the transaction.

Source versus destination
The source ownership lookup selects coins/keys that this wallet can spend. It is NOT
a destination requirement. Destination key lookup only displays an own-wallet warning;
no local key match is required to continue. Updated labels to explicitly say source
coin/source wallet key. Mx/checksum validation and repeated-destination confirmation
remain. The receiving address can be from another node/wallet with no local key entry.
The user's exact additional wallet/key-check screen is not yet identified; an optional
clarification was requested. Do not assume unrelated key-audit screens were corrected.
