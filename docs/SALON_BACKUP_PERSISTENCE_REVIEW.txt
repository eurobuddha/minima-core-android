Salon full-backup persistence review — 2026-10-18, source 1.9.88/159

Summary
A full restore prepares its messaging identity, profile draft and merged hosting
list, then saves them with one checked SharedPreferences commit. The new key is
activated only after that commit succeeds. Failed reads/writes have an explicit
four-language message. A cancelled or replaced owner cannot commit after staging.

Storage compatibility
Before the first successful full restore, hosting still uses
pandamonium_salon_hosting/hosting_profiles. Restore merges that complete list with
the incoming destinations, then writes salon_identity/me and
salon_identity/hosting_profiles in the same editor commit. Presence of the latter
key selects the combined store for all subsequent hosting reads and edits.
The legacy file is retained, and no key alias or encryption format changes.
A failed first commit removes the uncommitted selector when restoring memory;
a failed later commit restores the previous combined list. Corrupt combined data
never causes backup/restore to fall back silently to an older legacy list.

Android documents commit() as an atomic update whose true result means the new
values reached persistent storage:
https://developer.android.com/reference/android/content/SharedPreferences.Editor#commit()
Both preference locations remain covered by the host's allowBackup=false and its
explicit shared-preference exclusions for cloud backup and device transfer.
The user-exported version-1 backup format remains unchanged. Older integration
code predating this change does not read the combined hosting preference key.

Findings resolved
CRITICAL — Partial restore could activate a new key and then fail to save the
profile/destinations. All resulting records now share one checked commit. Key
preparation cannot activate a cache; cached messaging and derived Nostr identities
change only after successful persistence. Existing live-inbox/key-retention and
live-profile preservation rules remain intact.

MAJOR — apply() supplied no write result, while UI reported restored destinations.
The full restore uses commit() and propagates failure. Old editor widgets are reset
only by the successful completion path. The prior owner/lifecycle checks remain,
with an additional check after key preparation and immediately before committing.

MAJOR — Corrupt hosting data could be exported as an empty list.
Backup and restore now use a strict list read. Invalid JSON, trailing data, null
rows, empty/duplicate IDs and malformed exported profile/configuration fields abort
the operation without opening the save picker or discarding the stored data.

Locking
Restore acquires SalonComms, SalonStore, then HostingStore. Hosting CRUD is serialized
under HostingStore; its preference selector does not acquire SalonStore. Profile
reads now share SalonStore's lock, so they cannot observe a failed restore's
intermediate memory update. Concurrent hosting edits wait and use the selected
store after the restore. No new background worker or database is introduced.
