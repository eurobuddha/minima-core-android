Resolved findings
MAJOR — The old trust callback unconditionally upserted a captured mutable profile.
An account restore, saved profile edit or deletion could be overwritten by old
consent. Both the original account and complete destination snapshot are checked
before opening/accepting trust. Default selection is excluded from the endpoint
comparison, and the latest default is preserved by the pin-only update. Unsaved
editor changes invalidate consent. The original fingerprint remains literal.

MAJOR — Background tests read the live mutable editor and returned unowned UI
updates. They now use a deep copy of the accepted profile. Stored ownership is
checked before uploader creation, upload and fetch-back; UI results also check
screen generation, Activity lifetime and the current editor. An already-started
upload cannot be recalled; cancellation prevents subsequent steps and stale UI.
Repeated test requests cancel earlier ownership, and workers close uploaders.

MAJOR — Trust was treated as saved after an unchecked apply(). A checked commit
now precedes the retry. Storage failure restores the prior preference snapshot,
keeps the editor unpinned and shows the existing localized storage failure. The
same code works with legacy hosting preferences and the combined restored account
store. Corrupt profile lists are preserved, not replaced with a partial list.

The dialog is consumed before saving/retrying. Duplicate taps, dismissal, changed
accounts and render/destroy cancellation cannot retry or repin it. The setup-to-
trust handoff and pin-to-retry handoff hold the account lock throughout. Existing
pins cannot be silently replaced by the first-contact trust flow.
